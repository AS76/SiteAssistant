# Planning, layouts and maps area

Status: proposed functional specification. Imports, Gantt, viewers and updates described here are not yet implemented in the demo.

## Goal and structure

A project area with two connected sections:

1. **Planning and progress:** import a schedule, display it, record work performed and compare it with the plan.
2. **Layouts and maps:** preserve and display revisions of graphical documents, linking areas, assets, tasks and deviations to recognizable positions.

The site, areas and assets are shared by both sections. Selecting a task may open its layout; selecting an element on the map may show linked tasks, progress and deviations.

The later Engineering module reuses the same documents and revisions to link bills of materials and components; it does not create a second independent copy of layouts.

In complementary mode, the imported plan and source system statuses remain snapshots distinct from the current plan and internal actuals. Files may come from authorized references in an S3-compatible archive; acquisition does not imply a public copy or changes to the original. Real export profiles to be validated according to [Import and document archive](import-storage.md).

## Inputs and handling methods

| Input | First planned capability | Extensions |
| --- | --- | --- |
| Excel XLSX | Sheet/column preview, mapping, validation and versioned import | Reusable mapping profiles, revision comparison and other planning formats |
| CSV | Tabular import with explicit separator, encoding and mapping | Export/import profiles |
| Excel XLS and other legacy formats | Explicit conversion to XLSX or adapter to be assessed | Compatibility verified on samples, without assuming it from the file name |
| PDF | Original preservation, per-page viewing, zoom and separate links/annotations | Search and layers when present in the document |
| High-resolution images | Original preservation, preview and zoom | Tiled/multiresolution rendering for large files; formats and limits to be set on samples |
| CAD: DWG/DXF | Original preservation, revision and links; PDF or image preview provided or generated by a supported converter | CAD viewing with layers and coordinates, after verifying engine, licenses and compatibility |

Accepting and preserving a CAD file is not equivalent to viewing or editing it natively in the browser. No CAD editor is planned in the first increment. Conversions are separate processes with queued/processing/ready/error status; the original is not replaced. External conversion services require an explicit choice; files are not automatically forwarded to third parties.

## Planning: guided import

1. Upload the file and select the sheet, header row and date format.
2. Map the fields: stable identifier, description, WBS hierarchy, start/finish, dependencies, area/asset, responsible party/company, measurement method, quantity and unit where applicable.
3. Show a preview and rows to correct: duplicate IDs, invalid dates, finish before start, missing references, cyclic dependencies, inconsistent quantities/units.
4. Approve the mapping and create an immutable imported revision with checksum, provenance, author and reference date.
5. Explicitly choose which revision is the comparison baseline. Later corrections affect the current plan; a new baseline requires a separate action.

Sheets may contain formulas, but the system does not execute macros or code. Unavailable calculated values must be flagged and confirmed before import. An incompatible file does not produce apparently valid rows.

The new import uses stable identifiers, not row number or title, to recognize items. It shows additions, changes and missing rows; it does not automatically delete items or actuals. A previously imported file is recognized. Authoritative plan fields and actuals fields updatable in the app have separate write rules.

## Views

| View | Use | Updates |
| --- | --- | --- |
| Gantt | Dates, duration, hierarchy, dependencies, milestones; baseline/current-plan comparison | Open the item and update progress; date changes are recorded separately |
| WBS table | Structure and data of all items, with filters and groupings | Individual updates or guided entry of actuals; server-side validation |
| Board / lookahead | Upcoming work by area, company, responsible party and status | Operational coordination linked to the same items |
| Curves and summaries | Plan and actuals over time | Available when sufficient measurement, weights and history exist |

The Gantt is not the entire planning module: views use the same data. Work calendar, non-working days, site time zone and date semantics must be declared. The first increment does not promise resource optimization or a complete critical path engine. Any movement by dragging bars requires validation and an impact preview before changing dependencies or linked dates.

## Three progress methods

Each leaf item has an explicit method. The method may change only with migration of values and history, not by silently reinterpreting actuals.

| Method | Planned data | Operational update | Resulting percentage |
| --- | --- | --- | --- |
| Percentage | Target 100%, assessment criteria and weight | Record an absolute percentage between 0 and 100 with date and note | Recorded percentage |
| Quantity | Positive total and unit: pieces, meters or another defined unit | Add installed quantity per period, with author and references | Sum of valid quantities / planned total × 100 |
| Yes/no action | A single action and its completion criterion | Declare yes or no, preserving each change | No = 0%; yes = 100% of that item |

Entirely synthetic examples: 45%; 24 pieces installed out of 80 = 30%; check performed = yes. The yes value indicates execution of the single action, without automatically implying accepted verification or acceptance of an entire area.

### Update rules

- Record operational date, entry time, author, note and any evidence; option to link the update to the diary and shift.
- **Declared** and **verified** remain two distinguishable measures. The dashboard clearly labels which it is showing. Declared progress does not automatically close deviations or verifications.
- For percentages, values are absolute and are not summed across days. A correction preserves the previous value and reason. Backdated entries do not alter current data out of order without an explicit comparison.
- For quantities, entries are increments; corrections/reversals refer to the original entry. Check units and precision; pieces require integers. Verifications concern quantities actually declared, without double counting.
- A planned total greater than zero is mandatory for the quantity method. Exceeding the total is flagged and requires an explicit exception or revision; no silent capping at 100%.
- The no status may be explicit; absence of an update remains “not recorded”, distinct from a no declaration or 0%.
- Operation identifiers make retries and imports idempotent; version checks prevent silent concurrent overwrites.
- Actuals and verifications are recorded by the server with authorization and transactions, preserving previous events.

### Aggregations

WBS summary items are derived from leaf items. Summing quantities requires compatible units and meaning; aggregating different methods or types of work requires explicit weights. Proposed formula: `somma(peso × avanzamento) / somma(pesi)`, with positive weights and a declared population. Weight may represent comparable quantities, planned hours or an agreed technical weight. A simple average is not assumed to represent the project percentage. Missing data must be visible and the aggregate flagged as incomplete.

## Layouts and maps

- Preserve original, version, date, author, covered area, format, pages and graphical derivation status.
- Select the active revision without losing references to previous revisions.
- Link tasks, deviations and progress items to a page/area or a point/polygon. Coordinates always associated with the document revision.
- For PDF and images, use page/image coordinates, normalized or in a declared reference frame. CAD or geographic coordinates require explicit units, system and transformations: an uploaded drawing does not automatically become a georeferenced map.
- Annotations remain in a separate layer from the original. A new revision requires link verification, without automatically moving pins onto different geometry.
- For large images, generate previews and tiles with limits on dimensions/pixels and resources, loading only what the view needs. The high-resolution original remains available to authorized users.

## Proposed data model

| Group | Main entities and fields |
| --- | --- |
| Import | import_batches, source_mappings: checksum, mapping/version, source, outcome and rejected rows |
| Plan | schedules, schedule_revisions, schedule_items, schedule_item_revisions: stable external key, WBS, area/asset, baseline, dates and calendar |
| Links | schedule_dependencies, task_schedule_links: dependencies and associated operational work |
| Measurement | progress_items: method, unit, target, weight and acceptance criterion; link to the plan item |
| Actuals | progress_entries, progress_verifications: value, absolute/incremental nature, operational date, author, correction, evidence, verification status and idempotency key |
| Layout | layouts, layout_revisions: document_version_id, format, page, dimensions, units and coordinate reference |
| Derivatives | document_derivatives: preview, tiles or conversion, status, checksum and parameters |
| Annotations | map_annotations and typed links to task/deviation/progress_item, with foreign keys and the same site |

Binary originals and derivatives in private storage; structure, coordinates, relationships, progress and history in PostgreSQL. CAD processing and large images may require a separate worker process: resources and cost must be verified before introducing it. The initial app + database setup remains the first core.

## Proposed sequence and acceptance

1. **First increment:** XLSX with mapping, baseline and current plan, WBS/Gantt table, three progress methods and their events. Verify the plan → update → reload round-trip and declared/verified separation.
2. **Initial viewer:** PDF and images with revisioned originals and links to tasks/areas. CAD files preserved with an uploaded preview, explicit compatibility status and no promise of native rendering.
3. **Extensions:** supported CAD conversions, layers/coordinates, tiles for large images, dependencies and more advanced analysis; test on synthetic samples and verify licenses/resources.

Meaningful tests: reimport without duplicates or loss of actuals; baseline unchanged after updates; 24/80 = 30%; yes/no action with history; missing data distinct from zero; corrections and overruns; authorization; concurrent updates; separation between pins of different revisions; conversion error that leaves the original intact.

Representative Excel profiles, Gantt/calendar type, weights, verification policies and priority CAD formats remain to be agreed. Samples for development and the repository are synthetic.
