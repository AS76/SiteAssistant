The **HSE** view is the health and safety register of the selected site: near misses, accidents and observations. Every row records a fact — date, type, severity, location, number of people involved and measures taken — not the people themselves.

The register does not come from an import: rows are created, edited and deleted in the application. It holds no health data and is not linked to the employee record: people involved are **a number only**, never a name. A saved event can carry photos or PDFs, under an explicit rule: **photograph the condition, not the people**. See [Attachments on an event](#attachments-on-an-event).

## Reading the register

What it is for: knowing how many events were recorded, of which type and severity, and reading the measures taken.

1. Open **HSE** from the navigation, in the **Management** group.
2. Read the four counters at the top: **Near misses**, **Accidents**, **Observations** and **Total**.
3. Narrow the list with the **Type** and **Severity** menus and with the **From** / **To** period.
4. Read the table: **Event date**, **Event number**, **Type**, **Severity**, **Location**, **Persons involved** and **Measures**.
5. Clear the filters to return to the full list.

The list starts from the most recent event date. The counters cover **all** site events, not only those passing the filters. If the **From** date follows the **To** date, the view shows a message instead of the list: fix the period.

Under every date field the hint “Date: day/month/year” appears, the same in all filters and input forms: it says in which order the date is read, while the saved value stays in ISO format (`YYYY-MM-DD`). On a phone the **From** and **To** fields go one under the other at full width, each with its own label, instead of sharing the row.

## Types and severities

| Type | Meaning |
| :-- | :-- |
| Near miss | A close call: the event had no consequences, but it could have |
| Accidents | An event with consequences for one or more people |
| Observations | A behaviour, a condition or a tool worth reporting |

| Severity | Meaning |
| :-- | :-- |
| Low | No consequence or a negligible one |
| Medium | A consequence to manage, with no site stoppage |
| High | A relevant consequence or an immediate risk |

Type and severity are required choices. On creation the application proposes **Near miss** and severity **Low**.

## Adding or editing an event

Owners and editors see the **New HSE event** button.

1. Press **New HSE event**.
2. Choose the **Event date**, required.
3. Choose **Type** and **Severity**.
4. Add, if needed, **Event number**, **Location** and **Measures**.
5. In **Persons involved** enter a number only: if the count is unknown, leave the field empty.
6. Use **Factual notes** for what happened, without names or health information.
7. Press **Save HSE event**. The window closes, the counters and the list refresh and the message “HSE event saved” appears.

To correct a row, press **Edit** on the row: the same window opens with the current values and the button becomes **Save changes**.

| Field | Required | Limits |
| :-- | :-- | :-- |
| Event date | Yes | `YYYY-MM-DD` date |
| Event number | No | Up to 120 characters; unique within the site |
| Type | Yes | Near miss, Accidents, Observations |
| Severity | Yes | Low, Medium, High |
| Location | No | Up to 200 characters |
| Persons involved | No | Whole number from 0 up; no names |
| Measures | No | Up to 2000 characters |
| Factual notes | No | Up to 2000 characters |

An **event number** already used stays reserved after deletion: deletion is logical, the row leaves the list and the counters but stays in the audit register, and the number cannot move to another event. If the number is wrong, correct the row instead of creating a new one with the same number.

The **event number** is an internal reference: you can leave it empty, but when filled it must be unique within the site. Two events cannot share the same number, and the application rejects the save asking you to check the number.

## Attachments on an event

A saved event can have attachments: images or PDFs up to **15 MiB** per file. An attachment documents a condition — a missing guard rail, an unmarked edge, a load that swung — not the people.

1. Press **Edit** on the event: the **Attachments** section appears at the bottom of the window, below the buttons.
2. Press **Add photo or PDF** and choose the file.
3. If you want, write a **Description** up to 200 characters. It is used only for the check before upload and **is not saved**.
4. Check the warning, if it appears, then press **Save**: the window closes and the message “Attachment recorded” appears. Open **Edit** again to see the file in the section and open it with **Open attachment**.

The rule is written in the window and in the upload form: **photograph the condition, not the people**. No identifiable faces, no health data; if a photo is not necessary, you can attach a **diagram or pictogram**. The warning appears when the file name or the description contains words suggesting a person or an injury: it is a reminder for human review, not an examination of the image content, and it does not block the upload. The application does not recognise faces or diagnoses.

Upload is reserved to **owners** and **editors**. Removal is not available in the interface: it is API only, by owners and editors. If the event is deleted, its attachments stop being served: the list does not show them and the download returns “not found”.

Every opening of an HSE attachment writes a **Read** row in the audit register, with the file name. The row appears in **Latest changes** to owners and verifiers and is readable through the API; if the trail write fails, the download still works. Attachments on tasks and diary produce no read rows.

## Deleting an event

1. Press **Delete** on the row.
2. Check the date, type and any number shown in the confirmation.
3. Confirm with **Delete**.

The event disappears from the list and the counters, later reads and edits on the same row return “not found” and its attachments are no longer served. The row itself is not erased: it stays in the audit register, which keeps a copy of the event as it was plus a record of every creation, edit and deletion, with author and date. The trail is readable from the **Latest changes** panel in the view and through the API, by owners and verifiers: see [Latest changes](#latest-changes) and [Audit register](../../riferimento/api/#audit-register). If the event must stay readable in the interface, correct its data instead of deleting it.

## Latest changes

At the bottom of the view, owners and verifiers have the collapsible **Latest changes** panel: the twenty most recent entries in the HSE register, newest first. It is closed by default and the list loads when you open it.

1. Each row gives the action — **Created**, **Updated**, **Deleted** or **Read** —, who made it and when.
2. For a read, the name of the attached file; for the other actions the **event number**, or the first eight characters of the identifier when it has none.
3. For an edit, up to four changed fields appear as **field: before → after**; when more fields changed, the row says how many others remain. A read has no changed fields: it only says which attachment was opened.
4. When the list reaches twenty rows the panel warns that only the most recent changes are shown: to go further back use `GET /api/audit-events` with `limit` and `offset`.

Values are the stored ones: for type and severity you see the code (`near_miss`, `low`), not the translated label. The panel reloads every time you open it, so close and reopen it to see changes just made. Deleted events stay readable here, with the data they had before deletion. Editors and viewers do not see the panel.

## Who can do what

| Action | Role |
| :-- | :-- |
| Read the HSE register | owner, editor, verifier |
| Add, edit or delete an event | owner, editor |
| Open the attachments of an HSE event | owner, editor, verifier |
| Add or remove attachments on an HSE event | owner, editor |
| Read the latest changes | owner, verifier |

The **Attachments** section is in the edit window, which only owners and editors see; verifiers read attachments through the API. Removing an attachment is API only.

The `viewer` role has no access to the register: the entry appears in the navigation, but the view shows **Restricted register**. The register is separate from the other modules and feeds neither the Overview nor the report.

:::caution[If something does not add up]
- **“Restricted register” or no data:** your role on the site is `viewer`; reading is reserved to owners, editors and verifiers. See [Users and roles](../../amministrazione/utenti-e-ruoli/).
- **I cannot see the buttons:** only owners and editors write; verifiers only read.
- **Event number rejected:** another event of the same site already uses it. Leave it empty or change it.
- **Persons involved rejected:** the field accepts a whole number only, not text and not names.
- **Attachment rejected:** it must be a non-empty image or PDF, up to 15 MiB.
- **I cannot find the Attachments section:** it appears only when editing an event already saved, and only for owners and editors.
- **Period rejected:** the **From** date must not follow the **To** date.
- **Offline:** the view requires a connection, like the other module views; without a network you can neither read nor change the register.
- **Empty list:** the site has no events yet, or type, severity and period add up; clear the filters.
:::

The same rows are available through the API, with the `/api/hse-events` endpoints: see [REST API](../../riferimento/api/#hse).
